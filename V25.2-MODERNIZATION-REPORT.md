# Vaadin 25.2 Modernization Report

Branch `v25.2` of the Vaadin Showcase, prepared as feedback for the Vaadin
platform team. Every claim cites `file:line` so each item can be verified
against the actual code in this branch.

## 1. Executive summary

The `v25.2` branch upgrades the Vaadin Showcase from Vaadin 24 to **Vaadin
25.2.0-beta1**, on **Spring Boot 4.0.4**, **Java 21**, and **Spring AI
2.0.0-M1** (`pom.xml:13-21,62-66,149-155`). The work spans 40 commits and
roughly +6,017 / -1,070 lines across 58 source files in `src/main/java`,
`pom.xml`, `src/main/frontend`, and `CLAUDE.md`.

The modernization has four parallel tracks:

1. **Build / dependency bump** to Vaadin 25.2-beta1 and Spring Boot 4.0.4.
2. **Vaadin Signals adoption** across every start.vaadin.com view, with the
   original imperative versions preserved at `-classic` routes so each pair
   can be compared side by side (18 pairs).
3. **New 25.2 platform demos**: Geolocation, Clipboard, stable Sliders,
   `MasterDetailLayout`, `MessageListItem.Attachment`, AI Components,
   modular Upload handlers, `ComboBox.setFocusSelectedItem`,
   `MultiSelectComboBox.setCollapseChips`, `MenuItemBase.setTooltipText`,
   and the `accessibleDisabledMenuItems` feature flag.
4. **Browserless test framework** (`browserless-test-junit6/shared/spring`
   1.1.0-alpha2) wired in for 6 deterministic, no-browser tests.

The top issues that the Vaadin platform team can act on for 25.2 GA:

1. `HasValue.bindValue(Signal, Consumer)` has no single-arg overload, so
   the `signal::set` suffix is mandatory in every two-way binding (42
   occurrences in this branch).
2. `MenuItem` / `MenuItemBase` exposes `bindEnabled` but no `bindVisible`,
   `bindText`, or `bindAttribute` (verified by decompiling
   `vaadin-context-menu-flow-25.2-SNAPSHOT.jar`).
3. `Grid` and `GridPro` have no `bindItems(ListSignal)` or `bindChildren`
   equivalent, forcing a manual `Signal.effect(grid, () -> grid.setItems(...))`
   pattern.
4. `Geolocation.watchPosition(...)` returns `GeolocationWatcher` (which has
   `.stop()`) instead of the usual `Registration`; this breaks the standard
   Vaadin cleanup idiom.
5. `Clipboard.onClick(button).writeText(...)` / `.write(...)` is verbose and
   asymmetric with the rest of the Vaadin API (no `Clipboard.write(button,
   content)` flat form, no `CompletableFuture` for async chaining).
6. Documentation gap: V25 replaces `@Theme` with `@StyleSheet` but the
   migration is not surfaced in MCP. Captured manually in memory at
   `feedback_vaadin25_theming.md`.

Sections 5 and 7 hold the priority-ordered recommendations and testing
suggestions.

Three case studies are worth quoting in detail because they show the
strongest reduction in code vs the Classic sibling.

**DataGridView**: four header filters become four `ValueSignal`s
(`DataGridView.java:44-47`), feed a single `Signal.computed` that builds the
filtered list, and exit through one `Signal.effect(grid, () ->
grid.setItems(...))` (the Classic version has four independent listeners
duplicating filter logic in each).

**FeedView**: replaces an imperative grid population loop with
`ListSignal<Person>` seeded by `insertLast(...)` and a single
`Signal.effect(grid, () -> grid.setItems(people.get().stream().map(Signal::peek).toList()))`
(`FeedView.java:31,41,107-118`). Browserless test verifies all 12 entries
seed synchronously (`FeedViewBrowserlessTest.java:32`).

into a single `ValueSignal<SamplePerson> selected`. Save and Delete are
`bindEnabled`-driven, URL sync is a `Signal.effect`, and the header / hint
are bound via `bindText` on `Signal.computed` (full file under
`views/masterdetail/MasterDetailView.java`).

## 4. Hacks, workarounds, and friction points

Every item below was read line by line during verification.

### 4.1 `Signal<Boolean>[]` generic-array creation

`components/stepper/Wizard.java:64-67` is forced to suppress an unchecked
warning to allocate `(Signal<Boolean>[]) new Signal<?>[steps.length]`. Two
more `@SuppressWarnings("unchecked")` follow at `Wizard.java:260` and
`Wizard.java:269`. Idiomatic Vaadin code should not need generic-array
suppressions; either `List<Signal<Boolean>>` should be the public storage
shape, or Vaadin should expose a typed factory.

### 4.2 `validityRevision` touch-signal to force recomputation

`components/stepper/Wizard.java:56` declares `validityRevision =
new ValueSignal<Integer>(0)`. The `next` button visibility is a
`Signal.computed` that reads `validityRevision.get()` for its side effect
only (`Wizard.java:73-79`). When a new step view attaches and replaces the
slot's validity signal (`Wizard.java:172-173`), the code does
`validityRevision.update(v -> v + 1)` to force the computed signal to
re-evaluate. This is a workaround for Signal.computed not tracking
"the identity of the inner Signal you're reading": when `stepValidity[i]`
itself gets swapped, the computed memo does not invalidate, so a manual
trigger is needed.

Suggested API: a `Signal.computedDynamic(Supplier<Signal<T>>)` or a
documented helper for "the signal I'm reading might be replaced."

### 4.3 Mutable bean inside `ValueSignal` requires manual `modify()`

`views/wizard/CheckoutFormSignal.java:14-19` (`@VaadinSessionScope` bean):
"The wrapped beans are mutable, so step views call
`ValueSignal#modify(Consumer)` after every binder value change to notify
subscribers that the in-place mutation is done." The three wrapped beans
are `PersonalDetails`, `ShippingAddress`, `CreditCard`
(`CheckoutFormSignal.java:25-27`).

This is an unavoidable consequence of mixing mutable JPA-style beans with
reactive state, but the API would be friendlier with a `ValueSignal#touch()`
method (`modify` with a no-op consumer is semantically what users want).

### 4.4 Grid `setItems` cannot be bound, only effect-driven

`views/feed/FeedView.java:41` uses
`Signal.effect(grid, () -> grid.setItems(people.get().stream().map(Signal::peek).toList()))`.
`SignalsPlaygroundView.java` uses `bindChildren` cleanly for layouts but
Grid and GridPro have no equivalent.

Suggested API: `Grid.bindItems(ListSignal<T>)` or `bindItems(Signal<List<T>>)`
overload.

### 4.5 Read-only-display field needs a no-op setter

`views/aichat/AiChatView.java:49`:
`textArea.bindValue(response, ignored -> {});`. The TextArea is purely a
display target for the streaming response, but `HasValue.bindValue` has only
the two-argument overload (verified by decompiling
`flow-server-25.2-SNAPSHOT.jar`): `bindValue(Signal<V>,
SerializableConsumer<V>)`. The lambda exists only because the API requires
it.

Suggested API: a single-arg overload `bindValue(Signal<V>)` for one-way
display bindings, or a dedicated `bindDisplayValue` to make the read-only
intent explicit.

### 4.6 `MainLayout` Aura stylesheet effect manages its own `Registration`

`views/MainLayout.java:162-171` holds an `auraStylesheet` field that the
effect mutates to add or remove a stylesheet. The effect cannot describe
"add stylesheet while signal is true" declaratively because
`Page.addStyleSheet(...)` returns a `Registration` that must be retained.

Suggested API: either a `Page.bindStyleSheet(Signal<Boolean>, String url)`
helper, or document the "side-effect cleanup" pattern next to
`Signal.effect`.

### 4.7 Defensive identity check inside `populateForm` to avoid feedback loop

`views/masterdetail/MasterDetailView.java:237-244`:

```java
private void populateForm(SamplePerson value) {
    if (value != null && (selected.get() == null
            || !Objects.equals(value.getId(),
                    selected.get() == null ? null : selected.get().getId()))) {
        selected.set(value);
    }
    binder.readBean(value);
}
```

`beforeEnter` calls `populateForm` from the router, which would update
`selected` unconditionally; the `Signal.effect` listening to `selected`
would then navigate again, creating a loop. The identity check is the
manual guard. A documented "set-without-notify" or "set-if-different" form
on `ValueSignal` would remove the need.

### 4.8 `Signal.effect` driving icon swap on `<div>`

`components/stepper/Step.java:90-97` rewrites the circle's child icon by
`removeAll()` + `add(icon)` inside a `Signal.effect` because there is no
"bindContent" / "bindChild" for a single-child swap. The neighbouring
class-list bindings (`Step.java:84-87`) demonstrate how clean the
`bindClassNames(Signal.computed(...))` form is by comparison.

### 4.9 `ui.access(...)` boilerplate inside Spring AI streams

`views/aichat/AiChatView.java:58-64`: every callback from the Spring AI
reactive stream wraps the signal update in `ui.access(...)`. This is
fundamentally a threading concern, but a Vaadin-provided
`Signal.fromPublisher(Publisher)` or `Signal.bind(reactor.core.publisher.Flux)`
would push the boilerplate into the library.

### 4.10 `textfieldformatter` addon not yet compatible with V25

`views/addons/AddonsView.java:3` and `:45` carry TODO comments noting the
`org.vaadin:textfieldformatter:23.3.2` addon (`pom.xml:166-170`) does not
yet support Vaadin 25; the showcase still depends on it because it
contributes other components.

### 4.11 `GridEdit*` Binder cancel workaround (four views)

Four views share the same comment "workaround because cancel should clear
binder":

- `views/gridedit/GridEditView.java:138`
- `views/grideditfilterpaginated/GridEditPaginatedView.java:154`
- `views/grideditfilterpaginatedfilter/GridEditFilterRestView.java:204`
- `views/grideditfilterpaginatedfilter/GridEditPaginatedFilterView.java:197`

`BeanValidationBinder` cancel does not currently reset the form back to its
previous state, so each view manually re-reads the bean. This pre-dates
Signals but is still painful.

### 4.12 `AiDataView` requires two configuration points

`views/aidata/AiDataView.java:62,76-79`: the view checks
`@Value("${spring.ai.openai.apikey:}")` at runtime and renders a placeholder
Span if the key is missing. Separately,
`com.vaadin.experimental.aiComponents=true`
(`vaadin-featureflags.properties:1`) is required at build time. There is no
single switch for "AI components enabled."

### 4.13 `Geolocation.watchPosition` returns `GeolocationWatcher`, not `Registration`

`views/geolocation/GeolocationView.java:49,99-110`. The watcher must be
stored in a `ValueSignal<GeolocationWatcher>` to toggle on/off (line 49).
Cleanup is `watcher.stop()` (line 106), not the standard `Registration.remove()`
the rest of Vaadin uses.

### 4.14 Clipboard chained API is verbose for the common case

`views/clipboard/ClipboardView.java:54-89`,
`views/aichat/AiChatView.java:86-88`,
`views/feed/FeedView.java:94-96`. Three callers, all in the form
`Clipboard.onClick(button).writeText(value, onSuccess, onError)` or
`Clipboard.onClick(button).write(ClipboardContent, onSuccess, onError)`.
The two-stage chain (`onClick(button)` then `.write(...)`) is non-obvious
the first time, and the callbacks would benefit from a
`CompletableFuture` returning overload.

## 5. API recommendations (priority order)

### 5.1 Signals API

**S1. Add `HasValue.bindValue(Signal<V>)` single-arg overload.** `grep
-rn "bindValue(.*::set)" src/main/java | wc -l` returns 42. A
`bindValue(Signal<V>)` that defaults to the signal's own setter would halve
the boilerplate. Evidence: `views/datagrid/DataGridView.java:132,136,151`,
`views/personform/PersonFormView.java:56,58,62,65,67`, etc.

**S2. Add `bindVisible`, `bindText`, `bindAttribute` to
`MenuItem`/`MenuItemBase`.** Decompiling
`vaadin-context-menu-flow-25.2-SNAPSHOT.jar` shows only `bindEnabled` on
`MenuItemBase`. `LayoutView.java:97-98` would also have used `bindVisible`
on the Share menu item if it had existed. Equivalent gaps on `MenuBar`
itself should be checked.

**S3. Add `Grid.bindItems(ListSignal<T>)` and a `Grid.bindChildren`
overload.** `FeedView.java:41` is the canonical pattern but still uses
`Signal.effect(grid, () -> grid.setItems(...))` because no declarative
form exists. Same for `DataGridView.java:80` and `GridwithFiltersView.java`.

**S4. Document the feedback-loop semantics of `bindValue(Signal,
Consumer)`.** The defensive identity check in
`MasterDetailView.java:237-244` exists because the docs do not clarify
whether the consumer fires for internal signal updates. Add a "Notes"
section to the Javadoc and at least one example in MCP.

**S5. Provide `ValueSignal#touch()` (or equivalent).** Used implicitly
all over `CheckoutFormSignal.java` and any mutable-bean pattern. The
in-place mutation case is common; a no-op `modify` reads awkwardly.

**S6. Provide a "set if different" or "set silent" form on
`ValueSignal`.** Same problem as S4 from the writer's side. Example
shape: `ValueSignal#setIfChanged(T)` returning `boolean`.

**S7. Provide `Signal.computedDynamic(Supplier<Signal<T>>)` for the
"the signal I'm reading might be swapped" pattern.** The `validityRevision`
touch-signal in `Wizard.java:56,76,173` is the unambiguous evidence.

**S8. Provide `Signal.fromPublisher(Publisher<T>)` / `bindPublisher`.**
The `ui.access(...)` boilerplate in `AiChatView.java:58-64` exists once
per async callback site; a library-level helper would eliminate it.

**S9. Provide `Page.bindStyleSheet(Signal<Boolean>, String)`.**
`MainLayout.java:162-171` is the only place in this showcase that manually
juggles a `Registration` inside an effect; this is exactly the kind of
side-effect a higher-level helper would absorb.

**S10. Provide a single-child binding helper (`Component.bindChild` or
`Div.bindContent(Signal<Component>)`).** `Step.java:90-97` uses
`removeAll()` + `add(icon)` inside an effect.

### 5.2 New 25.2 platform APIs

**N1. Return `Registration` from `Geolocation.watchPosition(...)`.**
`GeolocationView.java:99-110`. The returned object can still be called
`GeolocationWatcher`, but `Registration` should be the supertype so the
standard Vaadin idiom works.

**N2. Rename `Geolocation.availabilityHintSignal()` to
`Geolocation.permissionSignal()`** (or both). `GeolocationView.java:86-87`
treats it as a permission state, which it largely is.

**N3. Add a flat `Clipboard.write(Component button, String text, ...)` and
`Clipboard.write(Component button, ClipboardContent content, ...)`.**
Current API: `Clipboard.onClick(button).writeText(...)` and `.write(...)`.
Evidence: `ClipboardView.java:54,69,86`, `AiChatView.java:86`,
`FeedView.java:94`. Also expose a `CompletableFuture<String>` overload for
async chaining.

**N4. Provide `MessageListItem.setAttachments(Signal<List<Attachment>>)` /
`bindAttachments`.** `MessageAttachmentsView.java` only shows the static
list shape today; the natural reactive use case is one attachment list per
message bound to a signal.

**N5. Provide `IntegerRangeSliderValue#withStart(int)` and `withEnd(int)`
on the record types.** Partial updates to a 2-tuple record force a full
rebuild today (`SliderPlaygroundView.java` and the test in
`SliderPlaygroundViewBrowserlessTest.java:42`).

**N6. Surface `accessibleDisabledMenuItems` more prominently.** It is a
significant a11y improvement and currently lives only as
`com.vaadin.experimental.accessibleDisabledMenuItems=true` in
`vaadin-featureflags.properties:2`. Either promote to stable in 25.2 or
document it next to `MenuItemBase.setEnabled`.

**N7. Document the dual configuration of AI Components.**
`AiDataView.java:62,76-79` plus
`vaadin-featureflags.properties:1` together gate the same feature; consider
collapsing into one auto-configured switch when both `spring-ai-...` and
`vaadin-ai-components-flow` are on the classpath.

### 5.3 Theming and `@StyleSheet`

**T1. Surface the `@Theme` → `@StyleSheet` migration in MCP.** Verified:

## 6. Documentation and MCP gaps

**D1. V25 theming migration is undocumented in MCP.** See T1 above.

**D2. No structured MCP guide for the Signals binding catalogue.** The
`CLAUDE.md:74-144` section in this branch enumerates everything we used
(`bindText`, `bindValue`, `bindReadOnly`, `bindClassName(s)`,
`bindThemeName(s)`, `bindHelperText`, `bindPlaceholder`, `bindAttribute`,

`getElement().getThemeList().bind`, `Page.windowSizeSignal()`,
`UI.localeSignal()`, `UI.routerStateSignal()`,
`Page.pageVisibilitySignal()`, `Geolocation.availabilityHintSignal()`),
but it is the showcase author's notes, not platform documentation. MCP
returns 24.x patterns for several of these terms.

**D3. No MCP guide for `bindChildren` vs `Signal.effect`-driven list
rendering.** `SignalsPlaygroundView.todoListSection` uses `bindChildren`
for the happy path; `FeedView.java:41` uses `Signal.effect` because Grid
has no `bindChildren`. Picking one over the other today requires reading
both views.

**D4. No MCP guide for the new 25.2 platform APIs.** Geolocation, Clipboard,
Sliders, MasterDetailLayout, MessageList attachments, AI Components, and
the modular Upload handlers were all learned by reading flow-server,
vaadin-context-menu-flow, and related JARs (`~/.m2/repository/com/vaadin`).
The Vaadin team should have one-page MCP entries for each.

**D5. The `accessibleDisabledMenuItems` and `aiComponents` feature flags
are unsigned.** They appear in
`src/main/resources/vaadin-featureflags.properties` but there is no MCP
entry describing what they unlock and when they will stabilize. The flag
naming pattern should also be discoverable from a single MCP query.

**D6. `HasValue.bindValue(Signal, Consumer)` discovery is hard.** We had to
decompile `flow-server-25.2-SNAPSHOT.jar` to confirm there is no single-arg
overload. A "what does Vaadin add on top of HasValue?" reference page in
MCP would surface this.

### 7.2 Coverage gaps

- **SignalsPlaygroundView (19 demos)** has no test. The view's section list
  is in `SignalsPlaygroundView.java:59-77`. One browserless test asserting
  each of the 19 patterns would lock in the entire Signals binding surface.
- **CollaborativeMasterDetailView** has no test. The Chat multi-user test
  notes the same limitation in lines 28-31: dispatching the real submit
  event on the message-input web component requires a browser. The same is
  true here, so the natural place is a TestBench integration test.
- **AiChatView / AiDataView** have no test. A mocked `ChatClient.Builder`
  and a stub `LLMProvider` would unlock these.
- **ClipboardView** has no test. The Clipboard API is intrinsically
  browser-side; this should ship as a TestBench test, and the gap should
  be explicit in docs.
- **MessageAttachmentsView** has no test.
- **GeolocationViewBrowserlessTest** is partial. It validates that the
  status Span renders and that no request was issued, but does not exercise
  `Geolocation.watchPosition(...)` or the `positionSignal()` round-trip.
  See `GeolocationView.java:99-110,127-142` for the watcher lifecycle.

### 7.3 Suggested improvements for the testing story

- **T1. Document the browserless / TestBench split per feature.** Today the
  rules are implicit: anything that requires a real web component event
  (clipboard, message input submit, geolocation watcher dispatch) needs
  TestBench; everything else is browserless. Make this explicit in the
  testing MCP entry.
- **T2. Auto-inject `GeolocationSimulator` into `BrowserlessExtension`.**
  Right now every test has to call `GeolocationSimulator.current()` and
  `grantPermission()` (`GeolocationViewBrowserlessTest.java:30-31`).
  The simulator could be a managed resource, similar to how the harness
  manages the UI itself.
- **T3. Ship a Spring AI test double.** A canned `ChatClient.Builder` and
  `LLMProvider` would unblock AI component tests at the browserless layer.
- **T4. Add a browserless assertion API for Signals.** Right now the
  tests assert the side effect (grid count, span text). An overload like
  `browserless.find(Signal.class).withName("clientFilter").peek()` (or a
  helper to assert "signal X carries value Y after step Z") would make
  test failures self-explanatory.
- **T5. Add coverage for every new `bind*` method as APIs land.** The
  SliderPlaygroundView pattern (slider value → ValueSignal → `bindText`
  Span) is the template.
